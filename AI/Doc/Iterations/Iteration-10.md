# Iteration 10 — 新聞爬蟲重建：從「只有標題」到可用的個股新聞流

**日期：** 2026-08-06

## 起點與方向修正

原訂目標是查明 `news_crawl_raw.published_at` 為何全為空字串。查證過程中發現
**該表根本不在 M2 的資料路徑上**——`model2_news._fetch_news()` 讀的是 `user_news`。
於是把範圍改為：檢查新聞爬蟲實際爬到什麼、找可用的公開免費來源、確認內文正常。

結果查出的問題比原本預期的嚴重得多。

## 一、舊爬蟲到底爬到了什麼

```sql
SELECT platform, count(*), sum(CASE WHEN content='' THEN 1 ELSE 0 END) AS 空內文,
       avg(length(content)) FROM user_news GROUP BY platform;
```

| 來源 | 筆數 | 空內文 | 平均內文長度 |
|------|------|--------|-------------|
| Yahoo Finance 台灣 | 69 | 50 | 133 |
| CNN Business | 52 | 50 | 9 |

三個問題，全部源自 `_parse_yahoo_soup` / `_parse_cnn_soup` 只解析首頁的連結文字：

1. **內文恆為空**——兩個函式產生的 dict 寫死 `'content': ''`。
   M2 的情緒分析從上線起就只看得到標題。
2. **tickers 恆為空**——`_auto_tickers` 用裸數字比對，在純標題上幾乎不命中；
   `stock_articles` 特徵因此恆為 0。
3. **沒有發布時間**——`insert_news_articles` 未寫 `submitted_at`，一律用
   `CURRENT_TIMESTAMP`，使時間衰減權重（T+0=1.0 / T+1=0.6 / T+2=0.3）
   把三個月前的舊聞當成今日新聞。

另外標題混入版型文字（「7 小時前」「52 分鐘前」），以及每次請求 `time.sleep(60~300)`
的禮貌延遲，使爬蟲實際上跑不完一輪。

## 二、來源盤點（公開免費）

實測 13 個候選，結果如下：

| 來源 | 狀態 | 內文取得 |
|------|------|---------|
| 鉅亨網 JSON API `news/category/tw_stock_news` | ✅ 採用 | **API 直接回傳內文**，不需抓原文頁 |
| Yahoo 個股 RSS `?s=CODE.TW` | ✅ 採用 | 抓原文頁；實測確實做個股過濾（含法說會公告） |
| 中央社財經 / 經濟日報證券・產業 / 自由財經 RSS | ✅ 採用 | 抓原文頁，實測 470~945 字乾淨正文 |
| Google News RSS（個股搜尋） | ❌ 不採用 | 個股標記精準，但 link 是 JS redirect，<br>base64 解碼與跟隨轉址皆無法還原原始網址 |
| 工商時報 `realtimenews-money.xml`、鉅亨網 `rss/tw_stock` | ❌ 404 | — |

## 三、實作（`Crawler/scrapers/rss_news_scraper.py`）

處理順序刻意為「鉅亨網 → 一般財經 → 個股定向」：鉅亨網內文隨 API 附帶、
不佔抓取預算，先處理等於免費多拿一批完整內文。

### 內文品質驗證（本迭代重點）

舊爬蟲從不檢查內文，「內文全空」才會從 Iteration 2 潛伏到現在。新增：

- `validate_content()`：長度、樣板頁字樣、中文字比例、字元變化度
- **抓取內文與 RSS 摘要必須相符**（`_matches_summary`，6-gram 重疊 ≥30%）
- 兩種來源用不同門檻：抓取原文 ≥120 字（低於此視為抓取失敗），
  RSS 摘要 ≥40 字（摘要本來就短，用同一標準會誤殺）
- 每則記錄 `content_kind`（api / body / summary），品質可追蹤

### 修掉一個會張冠李戴的 bug

首版保留了「全頁 `<p>`」的通用 fallback。實測發現 Yahoo 的排行類文章
`article` 容器為空，fallback 就把側欄其他文章的內文掃了進來——
標題是「8/4證交所盤後定價交易成交金額前20名排行」，內文卻是別篇報導。
**情緒與個股標記會被歸到錯的新聞上。** 已移除該 fallback，寧可退回摘要。

### 個股標記

`tag_tickers` 改為比對台股慣用標註格式（`（2330）`、`(2330-TW)`、`【2330】`）
與 `stock_info` 的公司名，且只回傳真實存在的代碼。
舊 `_auto_tickers` 會把「台股收在 44396 點」的 44396 當成股號。

## 四、實測結果（22 檔全量）

| 指標 | 舊爬蟲 | 新爬蟲 |
|------|--------|--------|
| 候選 → 保留 | — | 352 → 130 則 |
| 內文為空 | **100%**（最近 50 筆） | **0%** |
| 內文長度中位數 | 0 | api 757 / 原文 683 / 摘要 100 字 |
| 有發布時間 | 0% | 100% |
| 有個股標記 | 0 則 | 52 則，涵蓋 17/22 檔 |
| 內文與標題不符 | 未檢查 | 0 則（2 則被攔下改用摘要） |
| 單輪耗時 | 跑不完 | 約 4 分鐘 |

今日無個股新聞的 5 檔（2356、2367、2388、5483、6116）是真的沒有新聞，
不是抓取失敗——M2 現在會據此回報「無一篇提及本股」。

## 五、連帶發現：M2 在結構上無法區分個股

爬蟲修好後 `stock_articles` 確實隨股票變動（台積電 10、聯電 6、華邦電 6…），
但 M2 仍然 22 檔全 Buy。追進 `_features_to_signal` 才發現：

**五項評分輸入有四項是全市場聚合值，而 `stock_articles` 算出來卻從未被使用。**
規則引擎在結構上就不可能產生個股差異——這才是「22 檔全 Buy」的真正根因，
爬蟲問題只是讓它無從修復。

修正（`model2_news.py`）：

- 新增 `stock_sentiment_72h` / `stock_keyword_hit`：**只用提及本股的新聞**計算
- 評分主體改為本股情緒（權重 2.5），大盤情緒降為背景修正（權重 0.4）
- **無本股新聞時一律 Hold**——沿用 Iteration 9 對 M3 的原則：
  沒有證據就棄權，而不是拿大盤情緒冒充個股觀點
- confidence 依證據量打折（1 篇 0.6 倍，3 篇以上不打折）

| | 修正前 | 修正後 |
|---|--------|--------|
| M2 訊號分布 | Buy 22 | Hold 12 / Buy 8 / Sell 2 |
| 不同的 confidence 值 | 1 種 | 6 種 |
| 最終投票結果 | Buy 22 | Hold 12 / Buy 10 / Sell 2 |

## 誠實評估與遺留問題

1. **M2 的規則權重仍未經驗證**。本次是**結構性修正**（用本股新聞算本股情緒，
   這在邏輯上必然比用大盤情緒正確），不是調參優化。權重數值仍是猜的。
   新聞歷史僅數日，還無法用 Iteration 9 的走查方法驗證。
2. **XGBoost 仍未部署**。`XGBoost/train_m2.py` 的 300 樣本門檻尚未達標，
   但資料現在真的會累積了（每小時 130 則且帶個股標記），
   估計持續運行約一週後可首次訓練。屆時應與規則引擎比較後再決定是否部署。
3. **`user_news` 仍有 100 筆舊的空內文資料**（Yahoo/CNN 各 50）。
   未刪除——該表同時存放使用者手動提交的新聞，我無法完全區分兩者來源，
   刪除有誤刪風險。這些資料會在 72 小時後自動離開 M2 的時間窗。
4. **`news_crawl_raw` 的 published_at** 現在會寫入 ISO 字串，但該表僅為中介記錄，
   不在任何模型的資料路徑上（原始工單的假設有誤，記錄於此以免日後重複追查）。
5. 排程器目前**沒有在跑**。新聞要持續累積必須啟動
   `python main.py --mode schedule`。
