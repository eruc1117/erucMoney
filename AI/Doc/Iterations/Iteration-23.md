# Iteration 23 — 交易台帳：把持倉從「使用者填的數字」變成「可推導的結論」

**日期：** 2026-08-08

## 起點

Iteration 22 的持股只存一張「目前快照」：同一檔再次輸入就覆蓋。
這是刻意的最小可行版本，但它讓三件事算不出來——

1. **已實現損益。** 賣掉的部分賺賠多少，完全沒有留下
2. **分批進出後的成本變化。** 加碼會拉高平均成本，快照模式只能手算再手填
3. **決策的事後檢討。** 系統建議買進、使用者到底有沒有買、買在哪裡，無從對照

第三點是最值得補的。Iteration 21 已經開始記錄「模型當時預測了什麼」，
但沒有「使用者當時做了什麼」，兩邊對不起來。

## 一、台帳是事實，持倉是結論

新增 `user_trades`（日期、買賣別、股數、成交價、手續費、證交稅、備註），
`user_holdings` 改為由它**回放推導**。

每次新增或刪除交易，就把該股票的所有交易依日期重放一次，重算股數、
平均成本與已實現損益。

### 為什麼是回放而不是增量更新

增量更新在「新增一筆」時很簡單，但刪除或修改一筆早期交易時，
後面每一筆的平均成本都會變——增量算法只能整段重來。
那不如一開始就只留回放這一條路徑：程式碼少一半，而且重建出來的一定自洽。

### 成本基礎採移動平均法

```
買進：新平均成本 = (原股數×原成本 + 本次價金 + 手續費) ÷ 新股數
賣出：已實現損益 = 價金 − 賣出股數×平均成本 − 手續費 − 證交稅
      平均成本不變（賣出不改變剩餘部位的成本基礎）
```

**手續費計入成本、賣出的費稅直接扣在已實現損益上。**
不計費用的損益數字看起來永遠比真實情況好，那正是最該避免的自我欺騙——
Iteration 22 的週策略回測就是因為沒把 0.44% 的來回成本內建進目標函數，
才需要在報告裡另外提醒。

實測一組交易（買 1000@2100 → 加碼 1000@2400 → 賣 800@2440 → 出清 1200@2380）：

| 交易 | 交易後持倉 | 已實現損益 |
|------|-----------|-----------|
| 買 1000 @2100（費 2,993） | 1000 股 @ 2102.99 | – |
| 買 1000 @2400（費 3,420） | 2000 股 @ 2253.21 | – |
| 賣 800 @2440（費 2,782、稅 5,856） | 1200 股 @ 2253.21 | +140,797 |
| 賣 1200 @2380（費 4,070、稅 8,568） | 0 股 | +139,514 |

出清後持倉列消失，但**已實現損益 280,311 仍留在總計裡**——
快照模式做不到這件事，那筆錢賺了就不見了。

## 二、兩種模式並存，但不允許互相矛盾

不是每個人都想補完整的交易歷史。所以兩種模式都保留：

| 來源 | 用途 | 可否手改持倉 |
|------|------|-------------|
| `manual` | 快速填一個現況，不打算補歷史 | 可以 |
| `trades` | 由交易台帳回放推導 | **不行** |

有交易紀錄的股票，手動改持倉會被擋下並回 409：

> 2330 已有 3 筆交易紀錄，持倉由台帳自動推導；要調整請新增或刪除交易，
> 不要直接改持倉

允許手改結論等於允許事實與結論各說各話。反過來，一檔原本是手動快照的股票
一旦開始記交易，快照就會被清掉讓位給台帳——同樣是為了避免兩邊並存。

## 三、費用預設值可覆寫

依台股慣例預設手續費 0.1425%（最低 20 元）、賣出證交稅 0.3%，
但每一筆都能覆寫——券商折扣人人不同，把費率寫死會讓所有人的損益都是錯的。
表單即時顯示「實際支出／入帳」金額。

## 四、一個順手修掉的日期偏移

`user_trades.trade_date` 輸入 2026-05-12，前端顯示 2026-05-11。
原因是 node-postgres 把 `DATE` 轉成 JS `Date`，序列化時走 UTC 導致倒退一天。
改為 `trade_date::text` 直接送字串。

這類 bug 的麻煩之處在於它只在特定時區出現，而且差一天不會讓任何東西壞掉，
只會讓紀錄悄悄錯位。

## 誠實評估

功能完成且驗證過。這是一個沒有模型、沒有預測的迭代——
純粹是把記帳這件事做對，讓後續的檢討有事實基礎。

值得一提的是：本專案到目前為止，**唯一能穩定產出正確數字的模組都是不做預測的**
（風險模組的部位換算、持倉管家的紀律、現在的交易台帳）。
凡是嘗試預測方向的，走查一律不通過。這個對比本身就是資訊。

## 遺留問題

1. **無法修改既有交易。** 目前只能刪除後重新輸入。回放邏輯已支援，
   缺的只是 PUT 端點與表單。
2. **未處理除權息與股票分割對持倉的影響。** 配股會增加股數、除權會降低成本，
   台帳目前完全不知道這件事。`adj_close` 的還原係數其實已經有這個資訊
   （Iteration 18），可以自動生成調整交易。
3. **沒有和決策紀錄對照。** `voting_results` 有系統當天的建議、`user_trades`
   有使用者實際的動作，但兩者還沒有被放在一起看。
   這是本迭代真正想達成的目的，下一步應該補上「建議 vs 實際」的對照頁。
4. 賣超過持有量時不擋、照實算（多出的部分視為零成本），
   讓錯誤在報表上顯眼而不是卡住輸入。這是刻意的選擇，但沒有任何提示，
   使用者可能不會注意到自己漏記了一筆買進。
