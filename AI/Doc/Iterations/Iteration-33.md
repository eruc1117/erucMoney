# Iteration 33 — 美股的趨勢預測與預測比對

**日期：** 2026-09-13

## 起點

使用者要求「美股也要有趨勢預測跟預測比對功能」。

台股的這兩頁是同一條線：「趨勢預測」把 10 個跨股票 LSTM 套在一檔股票上，
「預測比對」把存下來的逐日收盤預測與後來的實際收盤比，附天真基準。
要讓美股也有，問題不在模型——跨股票 LSTM 的輸入是 z-score 後的收盤價視窗，
與價格尺度無關，直接套用就行——而在**整條線上每一個假設「價格在 `stock_daily_prices`」的地方**。

順帶處理了兩件啟動時發現的事，先記在前面：

1. **`start-dev.bat` 從未啟動排程器。** `--mode server` 不含排程，
   排程是另一個程序（`--mode schedule`），而 bat 裡沒有它。
   Iteration 32 加的 06:10／19:10／20:00 排程在服務關機期間從未執行，
   09-10、09-11 兩個交易日的台股／美股／期貨／指數全部漏抓。
   已手動用 `job_stock()`／`job_exogenous()` 補齊（與排程同一條路徑），
   bat 加上 Scheduler 視窗，ROOT 改成 `%~dp0`（原本寫死一個已經是空的 C: 路徑）。
2. **`us_gap` 台帳 09-09～09-11 三天是空的，補不回來。** 預測不能事後補——
   補了就是回顧不是預測。今晚 20:00 起才接續。

## 一、先問「美股該用哪個模型做趨勢」

Iteration 32 的 `explore_us.py` 已經量過：

| 目標 | 只用美股自身 | 加台股＋韓日 | 多數類別 |
|------|------------|-------------|---------|
| 全日（D 收 ÷ D−1 收） | 方向 50.26% | 方向 54.68% | 53.00% |

加亞洲盤的全日方向只贏多數類別 +1.68pp，低於部署門檻（2pp），
而且贏的那一段幾乎全在跳空——開盤後進場的人拿不到。
所以**不做新的美股趨勢模型**；「趨勢預測」在美股上用的是與台股同一批 LSTM，
目錄裡標 `credibility: none`，ModelBar 照樣顯示「無 edge」。
這與台股那一頁的誠實程度一致：Iteration 11 的結論是價格序列本身沒有訊號，
Iteration 32 在美股上得到同樣的數字（只用美股自身歷史，走查相關 0.0085）。

給一個標明沒有 edge 的曲線，比給一個看起來像訊號、實際是丟硬幣的模型好。

## 二、改動的是每一個「價格表」假設

同一張 `saved_predictions` 收兩個市場，用 `market` 欄分流（migration 014），
**不用 stock_id 的長相猜**——'TSM' 與 '2330' 剛好長得不一樣，但那是巧合不是規則
（與 `resolve_predictions.US_KINDS` 同一個理由）。

| 層 | 檔案 | 改動 |
|----|------|------|
| LSTM 推論 | `LSTM/serve.py`、`data_loader.py` | `market=us` 時讀 `us_daily_prices`；日期改為美東場次日期（見三） |
| 儲存／比對 | `Server/routes/predictions.js` | `MARKETS` 表：價格表、代號欄、台帳 target_kind、模型類型前綴四樣一起切 |
| 台帳 | `model_registry.py`、`resolve_predictions.py`、`model_lifecycle.py` | 新類型 `lstm_us:*`、新 target_kind `us_close`（回填去 `us_daily_prices`） |
| 目錄 | `model_catalog.py` | `lstm_us:*` 十個項目，頁面代號 `predict_us`／`compare_us` |
| 新鮮度 | `api.py`、`data.js` | `GET /data/freshness/exogenous`、`POST /data/backfill/exogenous`、`GET /us/tickers` |
| 前端 | `Prediction.jsx`、`PredictionCompare.jsx`、`api.js` | 兩頁各加「台股／美股」切換；美股標的用下拉（只有 12 檔）；重訓按鈕只在台股出現 |

**為什麼模型類型也要分開**（`lstm:m02` vs `lstm_us:m02`）：
模型檔相同，但台帳混在一起的話，同一個版本的線上 MAE 會是台幣與美元的平均，
「模型版本」頁上那個數字就沒有意義。分開之後，
美股的線上成績從零開始累積，與走查一樣得等 100 筆才過門檻。

## 三、美股的「日期」不能直接從明天開始算

台股的 `_next_trading_dates` 從明天起算。美股不行：

    台北時間 D 日白天，美股 D 日那一場（21:30 開盤）還沒開始，
    最新收盤是 D−1 → D 日本身就是第一個可預測的場次，跳過它等於白丟一天。

但也不能從「最後一筆資料的隔天」開始：資料落後時會產生已經開過的場次，
存進比對表立刻就「到期」，看起來像預測，其實是回顧。

規則：第一個場次 ＝ max(最後一筆資料的下一個平日, 今天（平日）)。
美國國定假日與台股一樣不處理，比對時以真實交易日對齊。
畫面與比對頁都註明「日期為美東場次日期」。

## 四、順手修到一個台股也有的 bug

`ensureLstmVersion()` 的 INSERT 把 `$1` 同時用在 VALUES 與子查詢 WHERE，
pg 回「inconsistent types deduced for parameter $1」，而外層 try/catch 只 `console.warn`，
結果是 `model_version_id = null`、台帳不寫。

台股從沒浮現，因為 `lstm:*` 的版本早就由 Python 端登錄過，永遠走到 `existing` 那條路。
美股是第一個真正走到 INSERT 的類型。修法是 `$1::varchar`。

## 五、比對改以真實交易日對齊（同日追加）

前端存下的預測日期是「跳過週末」推估的，國定假日不在裡面。原本 `compareRecord`
用日期精確匹配：假日那一列永遠不到期，**之後每一列都錯位一天**——
第 3 步的預測被拿去比第 2 個交易日的收盤。台股從 Iteration 21 起就是如此。

改成與 `resolve_predictions.py` 同一個定位法：第 i 筆預測 ＝ 基準日之後第 i 個真實交易日。
到期的列 `date` 改為真實交易日（保留 `planned_date`，明細表標「原估」），
未到期的列從最後一個真實交易日起再跳週末往後估；`matured_days` 改算
「第一個預測日起有幾個真實交易日」。不需要維護假日表——資料庫裡有哪一天，哪一天就是交易日。

驗證：拿 2330 存一筆跨端午（06-19 休市）的紀錄，06-19 那列對到 06-22，之後依序順延，
7 筆全數到期；部分到期的紀錄未到期列從最後真實交易日續推。驗完刪除。

## 誠實評估

- ✅ 兩個功能都能用，且與台股那條線共用同一套比對邏輯與天真基準。
- ⚠️ 它們給的是**參考曲線，不是訊號**。這不是這次做得不好，是實測如此：
  美股與台股一樣，價格序列本身沒有訊號。頁面上的「無 edge」標記是刻意留著的。
- ✅ 休市日不再讓比對錯位（第五節）。推估日期仍只跳週末，但比對以真實交易日對齊，
  與 Python 端台帳的回填口徑一致。
